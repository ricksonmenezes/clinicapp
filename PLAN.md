## What it is

A full-stack clinic scheduling and management platform with:
- A **backoffice web app** (Go backend + HTMX frontend) for clinic staff, consultants, and admins
- A **customer-facing web portal** where patients can self-register, browse services, and book appointments
- A **shared Go API backend** that serves both web (HTML fragments via HTMX) and mobile (JSON) from the same endpoints

---

## Core domain entities

| Entity | Notes |
|---|---|
| **Patient** | Profile, history, login credentials, package subscriptions |
| **Consultant (Clinician)** | Profile, commission config (global, per-service, per-session) |
| **Attendant** | Staff who serve sessions; no commission, listed on session record |
| **Service** | Priced item offered by the clinic; may require a consultant or be attendant-only |
| **Package / Promo** | A bundle of N sessions of a service, sold at a package price; has a principal consultant |
| **Session** | A single appointment instance; links to patient, service, consultant (nullable), attendants, and commission snapshot |
| **Invoice** | Generated per session or per package; PDF-printable; template customisable by admin |
| **Prescription (Rx)** | Generated by a clinician for a patient; printable |

## Phase 1 scope

### Module 1 — Authentication
- Email/password registration with email verification (token, 24h expiry)
- JWT access tokens (15 min) + refresh tokens (30 days, stored in DB for revocability)
- Web: tokens in httpOnly cookies. Mobile: tokens in JSON response body
- Client-type detection via `X-Client-Type: web | mobile` header; same endpoints, different response renderer
- Password reset flow (forgot → email link → reset → revoke all refresh tokens)
- Rate limiting on all `/auth/*` routes
- Role field on users: `patient | clinician | attendant | admin`
- Schema forward-compatible for future OAuth support (`user_providers` table scaffolded, unused —
  see "Unscheduled" under Phase 2 scope below)

### Module 2 — Patient management (backoffice)
- Create / view / edit patient profiles
- Patient history view (all sessions)

### Module 3 — Consultant & attendant management (backoffice)
- Create / view / edit consultant profiles
- Global commission % per consultant
- Per-service commission override per consultant
- Attendant profiles (no commission)

### Module 4 — Services & pricing
- CRUD for clinic services
- Price per service
- Flag: `requires_consultant` vs `attendant_only`
- Package/promo definition: N sessions of a service at a package price; assignable to a principal consultant

### Module 5 — Session management
- Record a session: patient, service, date/time, consultant (nullable), list of attendants
- Commission snapshot recorded at session time (which rate was used and why)
- Commission resolution order: session-level override → service-level override → consultant default
- Package sessions: commission follows the actual performing consultant per session, regardless of who the principal consultant on the package is

### Module 6 — Invoicing & PDF
- Invoice generation per session or per package
- PDF printing (server-side PDF generation)
- Admin UI with placeholder editor for invoice templates
- Payment history per consultant showing commission rate applied per session

### Module 7 — Prescriptions (Rx)
- Consultants can author Rx documents for patients via the backoffice
- Printable / PDF output

### Module 8 — Customer-facing portal
- Patient self-registration and login (same auth backend)
- Service browsing
- Calendar view: available vs. booked slots
- Booking flow: choose service → choose date/time → confirm
- Email notification on booking confirmation
- SMS notification on booking confirmation via **PhilSMS** — implemented in `internal/sms`
  (`PhilSMSSender`). Send endpoint: `POST https://app.philsms.com/api/v3/sms/send`
  (`Authorization: Bearer SMS_API_KEY`); developer docs:
  `https://app.philsms.com/developers/documentation`. Best-effort: unlike the email
  confirmation, a missing phone number or a PhilSMS send failure does not fail the booking.

## Key decisions and why

- **One backend, two clients.** The Go backend reads `X-Client-Type` from the request header and routes to a `ResponseRenderer` that either returns HTMX-ready HTML fragments (web) or JSON (mobile). Same business logic, same endpoints — no duplicate API surface.

- **JWT + refresh token pattern.** Access tokens are short-lived (15 min) to limit exposure; refresh tokens are stored in the DB so they can be individually revoked (logout, password reset). Web stores both in httpOnly cookies (XSS-safe); mobile receives them in the JSON body and stores client-side.

- **Email as unique identifier.** Lowercased on write, enforced unique at DB level. Future OAuth support will link to the same `users` row via `user_providers` — no breakage.

- **Commission resolution hierarchy.** Session-level override wins, then service-level override, then consultant default. The resolution used is always snapshotted on the session record so historical reporting is accurate even if rates change later.

- **Package commissions follow the performing consultant.** The principal consultant on a package record is informational only. Each session within a package records the actual performing consultant, and commission is calculated against that person — not the principal.

- **HTMX for the backoffice web UI.** No heavy JS framework. Go templates + HTMX keep the stack uniform (Go all the way down) and avoid a separate build pipeline.

- **Server-side PDF.** PDF generation happens in the Go backend (library TBD: `go-pdf`, `chromedp` headless render, or `wkhtmltopdf` via exec). Template placeholders are stored in the DB and editable by admin.

- **Monorepo.** Single repo, `backend/` and `web/` (HTMX templates + static assets) folders.

## Auth flows (Phase 1)

### Registration
```
POST /auth/register
  → validate email + password strength
  → check email uniqueness
  → bcrypt hash (cost 12)
  → insert user (status: unverified)
  → generate email verification token (UUID, 24h)
  → send verification email
  → web: redirect to "check your email" page | mobile: 201 JSON
```

### Email verification
```
GET /auth/verify-email?token=<uuid>
  → validate token (exists, not expired, not used)
  → mark user active, mark token used
  → issue access token (JWT 15 min) + refresh token (UUID, 30 days, stored in DB)
  → web: set httpOnly cookies, redirect to dashboard | mobile: 200 JSON with tokens
```

### Login
```
POST /auth/login
  → validate email + password
  → check user active (if unverified: prompt to resend verification)
  → bcrypt compare
  → issue access + refresh tokens
  → web: httpOnly cookies | mobile: JSON body
```

### Token refresh
```
POST /auth/refresh
  → web: read refresh token from cookie | mobile: from request body
  → validate (in DB, not revoked, not expired)
  → issue new access token; rotate refresh token
```

### Password reset
```
POST /auth/forgot-password
  → accept email; always return 200 (no email enumeration)
  → if user exists: generate reset token (UUID, 1h), send email

POST /auth/reset-password
  → validate token
  → validate new password
  → update hash; revoke ALL refresh tokens for this user
  → send confirmation email
```

## Middleware chain

```
ClientTypeMiddleware   → reads X-Client-Type, defaults to "web"
AuthMiddleware         → validates JWT; attaches claims to context; skips /auth/* public routes
RateLimitMiddleware    → per-IP limits: login 5/min, register 3/min, resend-verification 3/hr
```

Separately from the per-IP limits above, every email-sending endpoint (register,
resend-verification, forgot-password, reset-password) is also throttled **globally**, account-wide — see
`CLAUDE.md`'s Hard Constraints for the exact thresholds. This exists because Resend's free tier
(the chosen mail provider) caps outbound email at 100/day and 3,000/month regardless of which
user or IP triggered the send.

## Testing strategy

### Philosophy
All milestone verification is automated — no manual curl commands required. `go test ./...` is the
single command that confirms a milestone is done. Every module adds its own integration test file
before that milestone is marked complete.

### Layers

| Layer | Tool | What it covers |
|---|---|---|
| Unit tests | Go `testing` package | Pure logic: commission resolution, token generation, password hashing |
| Integration tests | Go `net/http/httptest` + test DB | Full request → handler → DB → response chain per endpoint |
| Email flow | FakeMailer (in-process) | Captures outbound emails in memory; tests extract tokens without calling the real Resend API |

### Integration test harness (scaffolded in M1, extended each milestone)

Located at `backend/tests/integration/`. Contains:
- `testserver.go` — spins up the full HTTP server with a real test DB and injected FakeMailer
- `testdb.go` — connects to `clinicapp_test` Postgres DB, runs migrations fresh per test run
- `fakemailer.go` — implements the `mailer.Mailer` interface; stores sent emails in memory
- `helpers.go` — shared assertion helpers, token extractors, request builders

Each module adds `backend/tests/integration/<module>_test.go`.

### Canonical M1 e2e test (the template all future flows follow)

```
Spin up test server with FakeMailer injected
POST /auth/register { email, password }
  → assert 201
  → assert FakeMailer has 1 email to that address
Extract verification token from email body (regex on the link)
GET /auth/verify-email?token=<extracted>
  → assert 200 / redirect
  → assert access token issued (cookie for web, JSON for mobile)
POST /auth/login { email, password }
  → assert 200
  → assert tokens in response
Hit GET /patients (protected) with access token
  → assert 200 (not 401)
```

### Testing the verify-email flow locally

There is no local SMTP sink in this stack — `internal/mailer` calls the Resend HTTP API
directly, even in local dev, using a Resend sandbox key. Sandbox emails never reach a real
inbox; they're visible only in the Resend dashboard (resend.com → Emails tab). To exercise
`GET /auth/verify-email` manually, copy the token straight from the DB or server logs and call
the endpoint directly (curl or browser) instead of clicking a link in an inbox.
